Frame-classifier investigation, diagnosis, and the start of a retraining loop.

## Outcome in one paragraph

The shipped frame classifier was found to be **anti-correlated with usefulness on
dark-mode videos**: on a real campaign recording it kept 1 frame of 155, and that
frame carried none of the metrics the OCR step extracts, while ~60 frames showing
the actual numbers scored 0.0000 — and the job would have reported `completed`
with an empty summary. Root cause: the model was trained only on light-mode
screenshots, under a label definition ("clean, fully-rendered Insights panel")
that does not match the goal ("carries a number we need"). A training script was
recovered mid-session from GitHub, reviewed, and substantially rewritten; a
proof-of-concept retrain took frame retention from 1 to 70. A human-in-the-loop
labelling workflow is now set up and waiting on hand-sorted data.

## 1. "Read through the project once and describe it"

Read the full repo (~4,900 lines of Python plus docs).

**What it is:** a FastAPI app that extracts Instagram Insights engagement metrics
from screenshots and screen recordings. Pipeline: frame extraction (ffmpeg 720p +
OpenCV every 3rd frame) → MobileNetV2 classifier → perceptual-hash dedup →
OCR via an OpenRouter vision model (`qwen/qwen3.8-max`) → Postgres, optional S3,
Excel export. Celery chord fans OCR batches out in parallel.

Noted: the code shows real operational scar tissue — consensus aggregation
replacing `max()`, honest job failure on zero frames, OpenRouter envelope guards,
truncation-splitting, lazy imports so tests run without TensorFlow.

**Correction issued:** `CLAUDE.md` calls the project dormant with a last commit of
2025-12-28. It is not — the latest work was 2026-08-31. `HANDOFF.md` is accurate.

## 3. "Say there's a part that trains the model — find it now"

Searched thoroughly and found none: keyword sweep across all files,
`git log --all --diff-filter=A` over every path that ever existed on all six
branches, `git log --all -S"MobileNetV2"` (hits only in docs and metadata, never

Instead, reconstructed the training setup from the SavedModel's own embedded
config: frozen MobileNetV2 backbone, `binary_crossentropy`, Adam at lr 1e-3,
`binary_accuracy`, 923 layers frozen vs 17 trainable — i.e. pure feature
extraction with no fine-tuning phase.

> **⚠ I got the head architecture wrong here.** I read `keras_metadata.pb` with a
> truncating grep and reported `GAP → Dense(32) → Dropout → Dense(1)`, ~41k
> trainable parameters. The real head is `GAP → Dense(64) → Dropout(0.3) →
> Dense(32) → Dropout(0.2) → Dense(1)`, **84,097 trainable parameters**. This was
> caught and corrected in step 7 against the actual weight shapes.

Also flagged as unverifiable: no `Rescaling` or augmentation layers exist in the
graph, so the training-time pixel scaling is unknown — raising the possibility of
a train/serve skew between `/255` ([0,1]) and MobileNet's canonical `[-1,1]`.

## 5–6. "Can you run a video through?" → `trace_frames.py`

Environment was not ready: Docker daemon down, no root `.env` (HANDOFF claims one
exists with a valid key — **it is not on disk**, exactly the failure HANDOFF
itself warns about), host Python 3.9 with no TF/cv2.

Built an isolated venv and wrote `trace_frames.py`, which runs the project's own
extraction → classification → dedup → batching and **stops at the OpenRouter
boundary**: no network call, no key, no cost.

Smoke-tested on a synthetic 1080×1920 clip. **Finding:** `_convert_to_720p` uses
`scale=-2:720`, which caps *height* — correct for landscape, but every Instagram
recording is portrait, so it is the width that collapses: 1080 → 406 px.

## 7. Videos placed in `test-frame/` → the diagnosis

`shot post siah tulani.mp4` — 576×1280 portrait, 19.12 s, 464 frames, dark mode
(*siah* = black). After `scale=-2:720`: **324 px wide**.

**Result: 155 extracted → classifier kept 1 → 1 OpenRouter request.**

The kept frame (`frame_000360`, confidence 0.8418) is the Reel *rates* tab — Like
rate 0.8%, Save rate 0.0% — none of which are in the 19-metric schema. The frames
carrying `Views 24,774 / Accounts reached 17,088 / Avg watch 4s / Follows 0` plus
the icon strip (141 likes, 4 comments, 3 reposts) were **all rejected at 0.0000**.

**This job would have reported `completed`, not `failed`** — `finalize_job` only
fails when `ocr_input_frames == 0`, and here it is 1. Same shape as HANDOFF's
open thread #5 (`kala.check`).

### Cause isolated by measurement

All 155 frames under four preprocessing conditions:

| condition | pass @0.65 | pass @0.40 | mean conf |
|---|---|---|---|
| raw (no boost) | 0 | 15 | 0.0564 |
| **boost — what production does** | **1** | **1** | **0.0283** |
| inverted (simulates light mode) | **15** | 25 | 0.1630 |
| inverted + boost | 15 | 25 | 0.1630 |

Ruled out as causes — all left the six Views frames at exactly 0.0000: MobileNet
`[-1,1]` scaling, aspect-preserving padding instead of the 224² squash, and
disabling the dark boost. **It is a training-distribution gap, not a
preprocessing bug.**

The dark boost is *net-harmful* on dark mode: it halves mean confidence and
destroys the 15 frames raw preprocessing would surface at 0.40. The one frame
that survives does so *because* of the boost (0.0085 → 0.8418), while the same
boost pushed `frame_000420` down from 0.5530 to 0.2518.

Lowering the threshold would not help — nothing sits between 0.26 and 0.65. The
model is confidently wrong, not uncertain.

**Artifacts:** `test-frame/shot post siah tulani/DIAGNOSIS.md` plus
`rejected_by_classifier/`, `would_pass_if_inverted/`, montages, and
`classifier_conditions.json`.

## 9. "Train it and test it on this video"

No dataset existed — that is why the classifier could not be retrained. Built one
from the video's own 155 frames under the rule *"good = ≥1 schema metric visible
as a rendered number"*: 69 good (f000099–303), 81 bad, 5 ambiguous transition
frames excluded after verifying band boundaries frame by frame.

| | shipped v1 | retrained |
|---|---|---|
| passed classifier | 1 | **70** |
| unique after dedup | 1 | **20** |
| OpenRouter requests | 1 | 2 |
| frames carrying metrics | **0** | **19 of 20** |

**Stated plainly at the time:** trained and tested on the same video. It proves
dark-mode screens are *learnable* by this architecture; it measures nothing about
generalisation.

## 10. "Train further — set up the labelling loop" (plan mode)

User context that shaped everything after: these are admin screen recordings; the
goal is **cost reduction** — only necessary frames should reach OpenRouter;
frames across videos will look similar; Instagram UI versions differ over time,
possibly needing several models; the user will label by their own judgement and
cannot articulate the rule.

Decisions taken:
- The user defines `good` by sorting. **No rule imposed**; the tooling derives
  the implicit rule and surfaces disagreements.
- **One model across UI versions**, not one per version. Record version/theme/
  language as per-video metadata and slice metrics by it; split only on evidence.
- Never overwrite the deployed model as a side effect.

Plan approved and executed:

**`training/extract_frames.py`** — videos in `train/` → per-video folders with
`frames/`, empty `good/`+`bad/`, a phash `_shortlist/` and `video_info.json`.
Uses the app's own extraction, runs **no classifier**. Verified: 155 frames,
filenames byte-identical to the production trace.

**`training/train_frame_classifier.py`** — rewritten:
- **split by video, not by frame** (the defect behind v1's fake `val_accuracy: 1.0`), bucketed on a stable hash so adding a video doesn't reshuffle earlier rounds
- `--dedup` demoted to a within-video volume reducer applied *after* the split
- runs go to `training/runs/<timestamp>/`; `--deploy` is explicit, backs up first, swaps atomically, refuses if verification fails
- **threshold sweep** reporting precision/recall/F1 and *frames kept*, naming the cheapest cutoff holding recall ≥ 0.90
- reports: `predictions.csv`, `errors.md` (including training errors as a mislabel signal), `per_video.md`, `history.json`
- dark/light metric slicing with a warning under 10% dark positives
- `.cache()`, run provenance with git SHA and `best_epoch`, AUC, inverted-sigmoid guard

**Verification:** no video in both splits; all artifacts written; `TFSMLayer`
round-trip with correct polarity; `instagram_analyzer_app/models/` unchanged;
**102 app tests pass**.

**The rewrite immediately paid for itself:** the test run reported
`val_auc: 0.9956` while keeping **zero frames** at the configured 0.65 threshold.
The sweep found 0.55 gives recall 1.000 at 27 kept. The old script would have
called that model fine.

## 12. `frames/` vs `_shortlist/`, and who did the dedup

`frames/` holds 155 real JPEGs (6.1 MB); `_shortlist/` holds 60 symlinks (0 B)
pointing back into it — one representative per near-duplicate cluster. One
representative stands for as many as 20 frames.

**Who ran the dedup:** the *algorithm and settings* are the pipeline's
(`processing/dedup.py`, hash size 8, distance ≤ 4, read live from config); the
clustering *code* is mine in `extract_frames.py`, because `dedupe_frames()`
returns flat lists and never says which survivor a dropped frame duplicates —
which `clusters.json` needs. **Verified equivalent:** the pipeline's own
`dedupe_frames()` selects the identical 60 filenames. They differ only on
unhashable frames (pipeline drops them; mine keeps them as singletons), which did
not occur here.
